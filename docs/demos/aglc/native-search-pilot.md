# AGLC native search pilot

This is a bounded front-end, not an activation receipt. Deployment, native content-source publication and a real keyword response are independently required. Do not alter production aliases, the external search destination, the reference brand release, search indexing policy, or CannabisSense to validate this branch.

## Configure the staged AGLC host

- Use the reviewed, English native Search Source backed by the existing Page template. Inspect data in the source Preview after review; this template is shared. Explicitly confirm which field holds the actual Sitecore item GUID in the native Search API response, and the source identifier used by the Search API.
- Set server-only `AGLC_SEARCH_INDEX_ID` to that source GUID on the staged AGLC runtime. Use existing `SITECORE_EDGE_CONTEXT_ID` or `NEXT_PUBLIC_SITECORE_EDGE_CONTEXT_ID` only if that ID has Search access. Otherwise configure an authorized Search-capable `AGLC_SEARCH_CONTEXT_ID` for the same environment. Do not enter credentials into the CMS datasource or commit them.
- Set `AGLC_SEARCH_ID_FIELD` only if actual item GUIDs are held somewhere other than `sc_item_id`. `AGLC_SEARCH_TITLE_FIELD` defaults to `Title` and falls back to the verified page title if omitted. Set optional `AGLC_SEARCH_SUMMARY_FIELD` only after finding a reviewed public summary field. Set `AGLC_SEARCH_LOCALE` only if the observed Search configuration requires it.
- Create/use a scoped Search Experience datasource template with a field named `search`; if using the [Configuration Manager](https://doc.sitecore.com/sai/en/developers/sitecoreai/search-experiences/copy-the-search-component-from-the-starter-kit.html), its field type is Plugin and field source is the installed Marketplace app ID. Its native datasource has `{"searchIndex":"<same source GUID>","fieldsMapping":{}}` initially; the rendering uses the server-validated source plus the reviewed host field mappings above. Set rendering `componentName` to `SearchExperience` and allow that component on the staged page's main placeholder.
- Compose a single English AGLC `/search-results` page under the existing AGLC home and include one accessible page heading (for example using PageIntro) above the SearchExperience rendering. Deploy the branch to the intended staged rendering host and, once approved, publish the results page and only the dependencies it needs on the staged Sitecore environment. Search is intentionally disabled in the editor and Preview.
- Verify results before touching the two CMS inputs. In the staged environment only, update the AGLC SiteHeader and Home Hero to `SearchAction=/search-results` (internal) and `SearchQueryName=q` after the direct route and results pass. The old `https://aglc.ca/search-results?opq=...` continues to work otherwise. No native wiring exists on CannabisSense.

## Required acceptance

1. From staged search results search for `forms`, `gaming` and `liquor`, see the corresponding published AGLC destinations and click through. Verify on desktop and mobile; test an unmatched string and a term that only matches CannabisSense. Then exercise **both** staged entry search boxes.
2. Confirm the actual native API has stable Sitecore item GUIDs and a complete bounded result set. The server accepts no more than 100 matching source rows, confirms the returned set is complete, and exposes only approved published AGLC item IDs (Home, Gaming, Liquor, Cannabis, Forms); it derives browser counts and safe canonical paths only after filtering. No raw third-party rows, counts, URLs, facets, draft inquiry or data source documents are returned. An incomplete response or unusable identity produces an unavailable state rather than an incorrect count. Revisit this pilot limit and the allowlist before scaling or retiring any of those public pages.
3. The request reaches native Search; it does not call a search analytics event or send browser cookies from this integration. The search phrase necessarily goes to the search service and appears in the requested page URL/browser history. Use rehearsed ordinary public terms and confirm the platform's handling before any production rollout. No new crawler or index/robots changes are required.

## Staged application fallback

Before native rendering definitions are published, the app can serve the same SearchExperience at `/search-results` using the published AGLC Home header/footer. It requires the same server-only `AGLC_SEARCH_INDEX_ID` above plus either `AGLC_SEARCH_FALLBACK_HOST` set to the exact staging request host (including a local development port if present), or `AGLC_SEARCH_FALLBACK_USE_VERCEL_URL=1` on a Vercel Preview with the matching `VERCEL_URL`. It is disabled on both known demo public aliases, all other sites/locales/paths, and draft sessions. A native published route always takes precedence. Start directly at `/search-results?q=forms`; neither existing CMS search box is rewired by this fallback.
